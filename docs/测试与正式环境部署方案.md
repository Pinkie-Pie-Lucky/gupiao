# 测试环境与正式环境部署方案

## 目标

将阿里云上的项目拆分为测试环境和正式环境，保证新功能、Prompt、数据源和数据库变更可以先在测试环境验证，再发布到正式环境。

## 可选架构

### 方案一：同一台 ECS，两个独立进程

- 测试环境监听 8094，正式环境监听 8093；
- 使用两个独立 `.env` 文件；
- 使用两个 PostgreSQL 数据库或两个 schema；
- 通过 Nginx 和不同域名转发，例如 `test.example.com` 与 `app.example.com`。

成本最低、改造最快，但两个环境共享 CPU、内存和磁盘，测试任务可能影响正式服务。

### 方案二：同一台 ECS，Docker Compose 双环境

为测试和正式环境分别维护 Compose 文件或 project name：

```text
docker-compose.test.yml
docker-compose.prod.yml
```

每套环境独立包含应用容器、Nginx 配置、环境变量、日志目录、缓存和数据库连接。容器化后部署、重启和回滚更一致，但底层 ECS 故障仍会同时影响两套环境。

这是当前项目较适合的过渡方案。

> 当前 ECS 已预装 Podman，因此实际采用 **Podman Compose** 执行同一套 Compose 文件。它与 Docker Compose 在本项目使用的应用、PostgreSQL、数据卷、健康检查与端口映射能力上兼容；仓库仍保留 Docker Compose 文件，后续迁移 Docker 无需改动应用代码。

### 方案三：测试 ECS + 正式 ECS

测试和正式使用两台独立 ECS，各自绑定域名、数据库、AI 配置、日志和缓存。隔离最清晰，测试不会抢占正式资源，也便于设置不同安全组和发布窗口，但资源成本更高。

如果正式环境已有真实用户，建议最终采用此方案。

### 方案四：容器化部署到 SAE / ACK / ECS 容器

将项目构建为 Docker 镜像，推送到阿里云 ACR，再通过 SAE、ACK 或 ECS Docker 部署。可以使用 namespace、service 或独立应用区分测试和正式环境，并进一步接入自动部署、灰度发布、扩容和回滚。初期配置复杂度和运维要求最高。

## 推荐实施路径

```text
第一阶段：同一 ECS + Docker Compose 双环境
第二阶段：测试和正式迁移到两台 ECS
第三阶段：接入 CI/CD、灰度发布和自动回滚
```

## 必须隔离的配置

| 项目 | 测试环境 | 正式环境 |
|---|---|---|
| 域名 | `test.example.com` | `app.example.com` |
| 端口 | 独立端口 | 独立端口 |
| 数据库 | 独立数据库 | 独立数据库 |
| `JWT_SECRET` | 独立测试密钥 | 独立正式密钥 |
| AI API Key | 测试 Key / 独立额度 | 正式 Key / 正式额度 |
| 缓存 | 独立 | 独立 |
| 日志 | 独立目录 | 独立目录 |
| 数据源缓存 | 不共享 | 不共享 |
| 发布分支 | `develop` / `test` | `main` / `release` |

正式环境不能依赖当前项目的内存仓储回退模式。测试和正式都应配置独立 PostgreSQL，否则服务重启后用户、关注列表、舆情持久化等数据可能丢失。

## 建议的发布流程

1. 从 `main` 创建功能分支并开发。
2. 合并到 `develop`，自动构建、运行 lint、测试和构建检查。
3. 部署到测试环境，验证页面、AI 接口、数据源、数据库迁移和回退行为。
4. 生成可追踪的版本号和变更记录。
5. 合并到 `release` / `main`，执行正式环境发布前检查。
6. 正式发布前备份数据库和当前镜像；发布失败时回滚到上一版本。

## Nginx、进程与健康检查

建议由 Nginx 负责 HTTPS、域名和反向代理，应用只监听内网端口。两套环境都应具备：

- `/health` 或等价健康检查；
- systemd、Docker restart policy 或 SAE 自动重启；
- 独立访问日志、错误日志和 AI 调用日志；
- 安全组只开放 80/443，应用端口不直接暴露公网；
- 进程启动时记录环境名、版本、Git commit、AI Provider、模型名和 Prompt 版本，但绝不记录 API Key。

## 数据库与备份

- 测试数据库不得连接正式数据库；
- 数据库迁移必须可重复执行，并在测试环境先验证；
- 正式环境启用定期备份、保留周期和恢复演练；
- 生产数据复制到测试环境前应脱敏；
- AI、行情和舆情缓存按环境隔离，避免测试结果污染正式数据。

## 需要用户确认或提供的内容

以下事项不能在没有授权和生产确认的情况下直接执行：

- 创建或修改阿里云 ECS、SAE、ACK、ACR、RDS 资源；
- DNS 解析、域名备案和 HTTPS 证书配置；
- 生产数据库迁移、停机和流量切换；
- 真实 AI Key、数据库密码、JWT 密钥等机密配置；
- 正式环境的删除、覆盖或回滚操作。

## 当前项目的建议起点

建议先在现有 ECS 上采用“Docker Compose 双环境”：测试使用独立端口、独立域名、独立 PostgreSQL 和独立 `.env.test`，正式保留当前域名和数据库但先补齐备份、健康检查和版本信息。测试环境稳定后，再迁移到独立正式 ECS。

## 个股分析 AI 调用排查补充

个股分析 AI 接口曾出现“重启后仍回退”的现象，原因分为两层：

1. 旧开发进程未真正退出时，接口仍返回旧的 `promptVersion`，因此新 Prompt 没有生效；
2. 新代码生效后，GLM 返回的内容虽然意图是 JSON，但在字符串值中直接插入了换行等控制字符，触发 `Bad control character in string literal`，于是进入确定性回退。

当前已确认：8093 接口返回 `promptVersion: sentiment-v4`，并且经过解析修复后 `aiStatus: completed`，测试请求已成功返回结构化 `viewpoints`。服务端现在会在 JSON 提取前折叠无语义控制字符，并在首次解析失败时发起一次“只修复 JSON 格式、不改变内容”的重试。

个股分析主汇总默认调用的是 `GLM_STOCK_RESEARCH_MODEL`；当前本地运行时为 `glm-4.1v-thinking-flashx`，而不是 DeepSeek。thinking 模型不支持 JSON mode，可能输出近似 JSON；服务端会改用常规 `GLM_MODEL`（当前为 `glm-4.7-flash`）进行格式修复。排查 token 用量时必须查看智谱 GLM 控制台中与 `GLM_API_KEY` 对应的账户/项目，而不是 DeepSeek 或另一个环境的 Key。Provider 控制台的用量统计也可能存在短暂延迟。

线上排查应优先查看：

- `agentMeta.promptVersion` 是否为当前版本；
- `agentMeta.aiStatus` 是 `completed`、`fallback` 还是 `not_requested`；
- `opinion.confidence.reason` 和后端 `[sentiment-agent]` 日志中的原始错误；
- Provider、Base URL、模型名和 Key 是否属于同一套环境；
- 测试环境和正式环境是否错误共享了缓存或旧进程。
